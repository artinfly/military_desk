# military_desk — «Военно-учётный стол»

Веб-версия АС «Военно-учётный стол» на Django + PostgreSQL: учётные карточки
работников, воинский учёт, справочники, перенос данных из старой программы и отчёты.
Проект в разработке.

В репозитории только код. Данные — вымышленные; реальные персональные данные
в репозиторий не попадают.

## Что нужно заранее

- Python 3.14
- PostgreSQL (16 и новее); папка `PostgreSQL\<версия>\bin` в PATH — драйвер `psycopg`
  использует библиотеку PostgreSQL оттуда
- git

Версии библиотек в `requirements.txt` — как на рабочем сервере.

## Установка с нуля

Команды выполняются в терминале из папки проекта (Windows).

1. Скачать проект:

   ```bash
   git clone https://github.com/artinfly/military_desk.git
   cd military_desk
   ```

2. Создать виртуальное окружение и поставить библиотеки.
   У проекта свой Python в папке `.venv`, чтобы его библиотеки не мешали другим проектам.

   ```bash
   py -3.14 -m venv .venv
   .venv\Scripts\python.exe -m pip install -r requirements.txt
   ```

3. Создать файл настроек `.env`: скопировать `.env.example` в `.env` и заполнить.
   `.env` хранит секреты этой машины и в git не попадает.
   - `SECRET_KEY` — получить командой ниже и вставить результат:

     ```bash
     .venv\Scripts\python.exe -c "from django.core.management.utils import get_random_secret_key as k; print(k())"
     ```

   - `DB_USER`, `DB_PASSWORD`, `DB_HOST` — пользователь, пароль и адрес PostgreSQL.
   - `DB_NAME` — имя базы (по умолчанию `military_desk_test`).

4. Создать пустую базу с именем из `DB_NAME` (например, в DBeaver:
   правой кнопкой по «Базы данных» → «Создать новую базу данных»).
   Django создаёт таблицы, но не саму базу.

5. Создать таблицы в базе:

   ```bash
   .venv\Scripts\python.exe manage.py migrate
   ```

6. Создать администратора (пароль вводится в терминале и не отображается):

   ```bash
   .venv\Scripts\python.exe manage.py createsuperuser
   ```

7. Запустить сервер разработки и открыть http://127.0.0.1:8000/
   (админка — http://127.0.0.1:8000/admin/). Остановить — Ctrl+C.

   ```bash
   .venv\Scripts\python.exe manage.py runserver
   ```

## После обновления кода

```bash
git pull
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe manage.py migrate
```

`pip install` ставит новые библиотеки, если они появились, `migrate` применяет
новые изменения базы.

## Структура проекта

Каждое приложение в `apps/` отвечает за свою область и содержит свои модели, страницы,
адреса, шаблоны, админку и тесты.

```
config/
  settings/        настройки: base.py (общие), dev.py (разработка), prod.py (сервер)
  urls.py          корневые адреса: админка и адреса приложений
apps/
  core/            каркас сайта: меню (navigation.py), главная страница
  accounts/        пользователи (своя модель User с отчеством и подразделением), вход, роли
  references/      справочники (18): общий шаблон Reference, реестр registry.py,
                   каталог, списки с поиском, добавление и правка
  personnel/       учётная карточка (Person) и её разделы: документы, адреса,
                   родственники, образование, назначения, доп. атрибуты
  military/        воинский учёт (MilitaryRecord: документ, ВУС, звание, военкомат,
                   бронирование), история приписки и увольнения забронированных;
                   массовые операции (services.py, страница «Операции»)
  reports/         отчёты в Excel (только чтение): реестр отчётов, численность для главной,
                   отчёт по фильтру
  legacy/          перенос данных из старой программы (import_legacy), нужен один раз
  demo/            генератор вымышленных данных (seed_demo), только для разработки
templates/         общие шаблоны: каркас страницы (base.html), вход, includes/ (формы, страницы)
static/            CSS (в стиле supply_service: тёмная панель, оранжевый акцент) и шрифт Golos Text
manage.py          команды проекта: runserver, migrate, createsuperuser, test и др.
pyproject.toml     правила форматирования black и isort
requirements.txt   библиотеки с точными версиями
.env.example       образец настроек для .env
```

Все страницы открываются только после входа. Новое приложение подключается в
`config/settings/base.py` (INSTALLED_APPS) и `config/urls.py`, свой раздел меню —
в `apps/core/navigation.py`.

## Справочники

Все справочники построены на общей модели `Reference` (`apps/references/models.py`):
название (уникальное), код, порядок и признак «Действует». Записи не удаляются, а
помечаются недействующими — на них ссылаются карточки. Код — номер записи в старой
программе и в выгрузке из кадровой системы; по нему загружаются и переносятся данные.

Новый справочник: модель в `models.py` и строка в `registry.py` — каталог, список,
форма и админка появятся сами. Смотреть справочники могут все вошедшие, добавлять и
менять — пользователи с правами Django на этот справочник.

## Учётная карточка и воинский учёт

`Person` (`apps/personnel`) — карточка работника: ФИО, табельный номер, личные данные,
работа. Разделы карточки — отдельные модели со ссылкой на неё. Воинский учёт
(`apps/military`) ссылается на карточку, а не наоборот: `person.military` — основные
сведения, `person.commissariat_history`, `person.rank_history` и т.д. — истории.
Ссылки на справочники защищены от удаления (используемую запись помечают недействующей).

## Список учётных карточек

`/people/` — главный экран: поиск по ФИО или табельному номеру и фильтры (работающие/уволенные,
военная обязанность, вид учёта, цех, военкомат, доп. атрибут, ВУС, офицеры, забронированные,
СВО, без воинского учёта). Фильтры сочетаются, по колонкам можно сортировать; адрес с фильтрами
можно сохранить в закладки. Логика поиска — `apps/personnel/services.py` (её же использует
отчёт по фильтру); модели `personnel` не зависят от `military`, а экран списка показывает и
воинские поля.

## Учётная карточка

`/people/<id>/` — карточка с вкладками: «Общее», «Воинский учёт» и разделы (документы,
адреса, родственники, образование, назначения, доп. атрибуты, приписка, увольнения
брони). Вкладка — в адресе (`?tab=addresses`). Добавлять, менять и удалять записи
могут пользователи с правами Django на соответствующую модель; правка любого раздела
отмечает в карточке, кто и когда её менял.

Разделы описаны в реестре `apps/personnel/sections.py` (модель, колонки, группа):
таблица, форма, добавление, правка и удаление для всех разделов — общие страницы.
`apps/military` регистрирует свои разделы сам (`sections.py`, `MilitaryConfig.ready()`).

## Главная и отчёты

На главной — численность по воинскому учёту (видна тем, кому доступен воинский учёт):
работающие, военнообязанные (из них офицеры и водители), бронь X4, команда R7, офицеры,
призывники без вида учёта.

Страница «Отчёты» (`/reports/`), всё в Excel:

| Отчёт | Что в нём |
|---|---|
| Численность | те же показатели, что на главной |
| ВУС по видам учёта | работающие военнообязанные: по каждой ВУС — X4, R7, H9 и всего |
| Форма бронирования | работающие военнообязанные без внешних совместителей и без источника приёма «ИК»; листы «Приложение 1» (ВУС с флажком «В перечне для приложения 1») и «Приложение 2» (документ воинского учёта с флажком «Отдельно в приложении 2») |
| Принятые с бронью и в команду | X4 и R7, принятые за период |
| Спец. уволенные | раздел «Увольнения забронированных», за период |
| Призывники | образование выше школьного, адрес, военкомат, должность |

«Отчёт по фильтру» — кнопка «Выгрузить в Excel» в списке карточек: те же люди, что в списке
(с теми же фильтрами и сортировкой), с колонками старой программы.

Устройство: `apps/reports/registry.py` — список отчётов (название, право, период);
`services/` — данные (`common.py` — кто считается военнообязанным, совместителем, водителем;
`counts.py`, `lists.py`, `filter_report.py`); `excel.py` — оформление книги. Новый отчёт —
функция в `services/` и строка в реестре. Перечень ВУС и документ для приложения 2
при установке размечаются миграцией по правилам старой программы и правятся в справочниках.

## Массовые операции

Меню «Операции» (`/military/operations/`, нужно право менять воинский учёт):

- **Смена группы учёта** — у всех незабронированных с выбранной группой ставится другая
  (или группа убирается).
- **Обновление спец. уволенных** — кто снова работает, убирается из увольнений
  забронированных; уволенные забронированные добавляются (удостоверение и дата
  увольнения); у всех уволенных снимается бронь.
- **Разбронирование по файлу** — файл Excel со СНИЛС (первая колонка, со второй строки)
  и номер приказа: работающим снимается бронь, ставится группа «Общий учёт» (код H9),
  записывается приказ, удостоверение очищается. Ненайденные СНИЛС показываются списком.

Каждая операция выполняется целиком в одной транзакции (`apps/military/services.py`).

## Роли и права

| Роль | Что может |
|---|---|
| Просмотр | смотреть карточки, воинский учёт и справочники |
| Оператор | смотреть всё; добавлять и менять карточки; добавлять, менять и удалять записи разделов карточки |
| Администратор учёта | всё, включая удаление карточек и правку справочников |

Роли — группы Django; описание — `apps/accounts/roles.py`. Группы с правами создаются и
обновляются сами после каждого `migrate` (или командой `manage.py sync_roles`). Роль
пользователю назначается в админке («Пользователи» → пользователь → «Группы»). Без роли
пользователь видит только главную; в меню — только доступные разделы.

## Перенос из старой программы

Команда `import_legacy` переносит данные из базы старой программы («stol», PostgreSQL):
справочники `nsi_*`, учётные карточки с личными данными и документами, воинский учёт,
приписку, увольнения забронированных и все разделы карточки. Старая база только читается.
Перенос — одной транзакцией: при ошибке в новой базе ничего не остаётся.

```bash
.venv\Scripts\python.exe manage.py migrate
.venv\Scripts\python.exe manage.py import_legacy --host <адрес> --dbname stol --user <пользователь> --dry-run
.venv\Scripts\python.exe manage.py import_legacy --host <адрес> --dbname stol --user <пользователь>
```

Пароль к старой базе спрашивается при запуске (или берётся из переменной окружения
`LEGACY_DB_PASSWORD`). `--dry-run` — пробный перенос с откатом: только итог по таблицам и
список проблем. Перенос идёт только в базу без карточек; `--replace` удаляет карточки
и переносит заново (справочники не дублируются).

Как переносится:

- справочники сопоставляются по коду (номер записи в старой базе), затем по названию;
  удалённые — «не действует»; виды учёта X4/R7/H9 — «Спец. учёт», «Команда», «Общий учёт»;
  офицерские звания и флажки формы бронирования размечаются сами;
- дата 31.12.2099 означает «без окончания» (не уволен, текущая приписка, текущее назначение);
- даты до нашей эры («0001-01-01 BC» — так старая программа записывала пустую дату)
  и ссылка на справочник с номером 0 (значение по умолчанию) считаются пустыми;
- записи, помеченные в старой программе удалёнными, не переносятся;
- цех и должность — из последнего назначения, иначе из `curr_dep`/`curr_position`;
- не переносятся: пользователи старой программы (вход — учётными записями Django),
  таблицы 1-го отдела (`spr`, `spr_cats`, схема `firstdep_reports`), служебные таблицы
  и таблицы, которые в старой программе не заполнялись: разделы «Звания», «Служба», «Сборы»,
  «Присяга», «Снятие с учёта», «Награды», «Спецучёт», «Языки», «Профессии», «Пропуска»
  и пустые справочники (виды деятельности, должности в армии, семейное положение, филиалы,
  языки, кем выданы, профессии, причины снятия, награды, производства, статусы и категории
  работников). В проекте их нет;
- пока не переносятся: вкладка «Ещё» (`additional_personal_properties`) и документы,
  адреса и прочие таблицы родственников (`relatives_*`).

## Демо-данные (только для разработки)

```bash
.venv\Scripts\python.exe manage.py seed_demo --count 2000
```

Заполняет справочники и создаёт вымышленные учётные карточки со всеми разделами и
воинским учётом (`apps/demo`). `--seed N` — повторяемый результат, `--clear` — удалить
прежние карточки. Приложение `demo` подключено только в настройках разработки, на
сервере команды нет.

## Настройки разработки и сервера

`manage.py` по умолчанию использует `config.settings.dev` (режим отладки),
`wsgi.py` (gunicorn) — `config.settings.prod`: отладка выключена, адреса сайта
(`ALLOWED_HOSTS`) обязательны, статику раздаёт whitenoise.

Запуск на сервере:

```bash
export DJANGO_SETTINGS_MODULE=config.settings.prod
python manage.py migrate
python manage.py collectstatic --noinput
gunicorn config.wsgi --bind 127.0.0.1:8000
```

За nginx в `.env` сервера задаются `USE_X_FORWARDED_HOST` и `CSRF_TRUSTED_ORIGINS`;
если несколько сервисов открываются по одному имени — свои `SESSION_COOKIE_NAME`
и `CSRF_COOKIE_NAME` (см. `.env.example`).

## Тесты и форматирование

```bash
.venv\Scripts\python.exe manage.py test
```

Django создаёт временную тестовую базу, поэтому пользователю PostgreSQL нужно право
`CREATEDB`. Код форматируется black и isort (в VS Code — при сохранении файла).
